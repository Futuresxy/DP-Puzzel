# 文档版本与维护规则

本规则按用户最新要求简化历史展示，使规格正文能够直接用于实现和评审。

## 1. 版本含义

| 版本形式 | 用途 | 示例 |
| --- | --- | --- |
| vM.N | 主要架构版本；数值、接口、周期或资源合同改变 | v1.3 → v1.4 |
| vM.N.x | 同架构下的说明、映射、排版和非核心修订 | v1.4.1 |

架构版本由整套合同共享，各文档的小修号可独立增加。版本号不代表全部待决项获批，也不替代验证证据。实现报告记录模型/测试/输入指纹及对应 spec 版本；Git 提交保存完整内容快照。

## 2. 正文与历史

**正文以当前有效定义为主。** 删除过时草案、失效流程和重复的“当前定义”段落，不为每次小修保留划线副本。

仅当发生核心架构变更时，在相关文档保留“上一主要版本 → 当前主要版本”的简短删除线对照。最多展示相邻两个主要版本；再早内容归入 Git 历史，不继续叠加。非核心小版本的措辞、链接、格式和状态修正直接更新正文。

核心变更的对照必须说明原因及影响，不能只列旧文件名。总记录保留两版摘要、当前文件索引和必要提交链接；不再复制每一版的完整索引。

## 3. 页首和排版

每份 spec 的第一行继续包含功能、范围、固定版本、修改时间及时区、对应代码。实现未建时明确写未实现，不用 README 冒充代码。

```text
> 功能：…；范围：…；版本：v1.4.1；修改时间：YYYY-MM-DD HH:MM:SS +08:00；对应代码：实际文件链接或未实现状态。
```

其后使用单一一级标题、简短导语和按逻辑顺序组织的二级标题。表格表达接口、参数、流水和比较；公式单独成段；标识符使用代码字体。避免密集历史告示、重复状态、无意义装饰和过长段落。跨页通过链接复用定义，不重复维护整份合同。

## 4. 修订流程

1. 确认属于架构变更还是同架构修订，更新版本和时间。
2. 修改当前定义；核心变更按上一节保留一组必要对照。
3. 同步受影响的源码、参数、测试与[总版本记录](CHANGELOG.md)。
4. 核对元信息、公式、表格和本地链接；通过相关检查后提交分支与 PR。
