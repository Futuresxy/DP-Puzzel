# Spec 版本与修订维护规则

状态：用户已要求所有当前新版 spec 使用固定版本、页首元信息、架构时间线和删除线修订。本轮为现有文档建立 v1.0 基线，不把未决设计转为已确认，也不开始 CModel/RTL 实现。

## 适用范围与版本

本规则适用于根目录 `src/spec/**/*.md` 的全部当前规格、索引、模板和变更记录；新增规格按同一规则建立。旧 `hw/spec/` 属于历史归档资料，继续保留原版本、证据归属和状态。外部标准的版本单独记录，不与本项目版本号混用。

- `v1.0`：本轮首次建立的架构文档基线。版本号本身不代表已冻结或验证通过，确认状态仍以各条要求及文档状态为准。
- `v1.0.1`、`v1.0.2`：同一架构版本内的文档修订，追加 `.x`。适用于说明补充、拼写/链接/映射更正，以及不改变已生效合同的候选讨论记录。
- `v1.1`：局部架构、资源组织或已生效接口/数值/周期合同变更。开始新的架构版本时，文档修订后缀重新从无后缀基线开始。
- `v2.0`：整体架构重做或主要计算边界、层级、数据流替换。大小版本均需记录原因和影响，不仅改页首数字。

`vM.N` 为整套规格的架构版本，同架构下各文档独立推进其 `.x` 修订号；未修改的文档无需增加修订号。进入新架构版本时，在总时间线列出受影响文档与承接关系，并同步整套当前规格的架构版本字段；未改变正文的文档记为版本承接，不伪称发生了设计修改。

版本不能替代内容快照。后续实现及验证记录采用 `spec_id=dp-cube/vM.N@<git-commit>`，并引用该提交中实际文档版本；同一架构版本下不同修订的文档集合由 Git commit 唯一确定。配置与实现版本分别记录。

## 每份文档的第一行

第一行统一使用可见的 Markdown 引用行，包含以下字段，不在前面插入标题、空行或隐藏注释：

```text
> 功能：本文定义什么；范围：层级、模式及边界；版本：v1.0；修改时间：YYYY-MM-DD HH:MM:SS +08:00；对应代码：CModel/Chisel/Verilog 的文件或明确未实现状态。
```

第二行留空，其后保留标题、状态与正文；已有历史状态提示可以放在标题前。修改时间为本次文档修订批次的时间，显式保留时区；历史记录沿用真实时间。旧元信息通过追加时间线保留，页首始终展示当前值。

对应代码必须写真实路径及角色。模块已实现后列出具体 CModel 文件、Chisel 文件、手写 Verilog 文件，必要时增加共用验证与生成 RTL 的映射。模块尚未实现时，列出现有入口并明确“模块文件未建 / 文件映射待定义”，不能构造文件名或把 README 当作实现代码。只有规范管理功能的文档明确写“无运行时代码”。

## 正文修订保留旧文字

修改已存在的定义时，原文字保留为 `~~旧文字~~`，紧接新定义、版本、时间和原因。删除线旧文字为历史记录，不能作为当前实现或验证依据。新增定义可以直接追加，并在时间线说明其状态。

普通段落使用以下形式；多次修改继续追加，不能覆盖前次记录：

- ~~旧定义~~ → **v1.0.1 当前定义：**新定义。（修改时间、原因/依据）
- ~~v1.0.1 的定义~~ → **v1.1 当前定义：**再次修订后的定义。（架构变更时间、原因/影响）

表格修改保留旧行，每个被替代的单元格分别加删除线，并标明“已替代”；新行写当前定义与版本。公式或短代码使用 `~~` 包住整个行内代码，例如 ~~`M={h,F,0}`~~ → `M={h,F}`。代码块内部的 `~~` 不会渲染成删除线，因此旧代码块改为逐行引用/行内代码并加删除线，随后列出当前代码块。旧图/流水表保留并标明版本与失效范围，新图表另列；图中旧规则的文字说明也需有删除线对照。

局部短修改优先在原位置对照。旧版段落/图表过长时，可完整保留在同一文档的“历史修订对照”，在原位置链接当前定义与历史记录；不得只删除旧内容后声称 Git 可追溯。候选被否决或待决问题被解决，同样保留原状态并标明新状态和依据。

首次建立版本管理前，已被覆盖的历史内容可从 Git/用户确认记录恢复；必须标明“未编号（追溯）”或“原候选”，不编造当时不存在的版本号、批准状态或精确时间。本轮已恢复关键解包、scale、C/last、模式配置和 INT8 延迟的对照，完整旧稿仍由对应 Git 提交提供。

## 每份文档的时间线

文末追加“版本与架构时间线”，每条至少包含：版本、修改时间、类型、修改内容/原因、来源。架构变更另写影响的模式、参数、端口、数值结果、流水级、资源共享以及 CModel/两套 RTL/验证需同步的内容。即使变更发生在同一天，也用版本和实际时间区分。

总时间线在 [CHANGELOG](CHANGELOG.md)，每个文件保留自己的时间线。已确认要求、算术推导、候选和待决项继续明确区分；旧候选恢复为删除线不表示它曾是生效架构。

## 更新顺序

1. 判断是同架构修订还是架构合同变更，确定版本与时间。
2. 在改动位置保留旧文字删除线，写新定义及原因/依据，并更新受影响的交叉引用。
3. 更新页首功能/范围/当前版本/修改时间/真实代码映射，追加该文档时间线和总时间线。
4. 数值、接口或周期合同改变时，同步 CModel、Chisel、手写 Verilog 与共用验证的对应描述；尚未实现的部分继续保持未实现状态。
5. 检查元信息、版本、时间线、删除线对照和本地链接，审阅差异后按仓库分支/PR 流程提交。

新文档使用 [TEMPLATE](TEMPLATE.md)。
